# GPU 导出优化阶段总结

2026-11-17 后续接入：普通导出窗口为原生合成工程默认选择 GPU 加速，并提供兼容模式；使用8帧队列与导出期间不限帧，完成/取消/失败恢复预览设置。唯一build安装与检查以最新本机记录为准。下方是接入前诊断阶段实测和还原点，174.92秒不能自动当作新安装包的实测值。

## 已完成的实现

- 逐阶段 CPU 墙钟计时与真实场景固定区间诊断，区分状态往返、渲染提交、回读、颜色转换、PNG、写管道、准备和收尾。CPU 提交时间不能当成 GPU 执行时间。
- GPU 显示颜色/方向转换、D3D11 有界纹理池和异步 NVENC 出口，绕过完整画面回读、CPU 逐像素转换和 PNG 中转；复用现有混音与 MP4 封装。
- 仅测试实例可用的不限帧开关、原生提交/输出锁与 API 分段计时；`mergedFrame` 合并状态应用与捕获往返。
- 小批量不可变状态队列，支持 1/4/8 帧额度、每批最多4帧、2MiB状态预算。额度覆盖待执行、在途与未回收结果，会话号隔离迟到请求；取消安全排空当前帧。
- `fullProject:true` 要求 GPU+合并、4/8帧队列、新目标和完整工程范围，上限216,000帧。全片报告保留有界汇总与少量样本，原生记录及 sidecar 校验采用流式处理；仅全片控制超时扩至30分钟。

保留单张最终画面纹理、已有8槽编码池、媒体/场景/settle等待和原生 Accepted 生命周期约束。未实施多画面缓冲，不允许通过覆帧或跳过资源就绪获取吞吐。具体协议、硬件条件和构建方法见 [GPU 原型](../../native/gpu-export/README.md)与[架构](architecture.md)。

## 性能证据

早期真实场景中 ReadDisplay+PNG 约占逐帧墙钟68%～74%，其中 CPU gamma约66～75ms、PNG约46～76ms、ReadPixels约22～43ms；不能全部归因于GPU回读。

| 对照 | 结果 |
| --- | --- |
| 第一轮真实短片，原PNG与GPU路径 | 逐帧3.60～4.35→12.08～13.88fps |
| 同Player合并状态与捕获，两轮 | 逐帧85.66→100.66fps；10秒短片总耗时9.23→8.89秒 |
| 同Player合并与8帧队列，两轮短片 | 逐帧113.03→271.92fps；10秒短片总耗时8.137→6.658秒 |
| 三段60秒成片，合并与8帧队列 | 平均总耗时21.144→12.805秒 |
| RTX4090完整21:05.03影片，1080p/30fps | 37,951帧，端到端174.9211秒，约7.23倍实时 |

不同轮次、片段和运行条件的数值不能连乘成总加速倍数；完整影片只有一次实测，没有完整旧路径对照。GPU使用H.264 High/P4 HQ/QP18、无B帧/无lookahead，QP18不等价于旧x264 CRF18。

全片准备5.1102秒、画面124.9091秒、编码排空/音频/封装44.5515秒，阶段间另有少量开销。应用启动和载入另计8.5122秒；导出后的解码验证不计入导出时间。收尾尚未细分，不能把44.55秒全算作编码器耗时。

## 正确性与未决事项

队列矩阵14,400对对应画面及配对音频解码一致；实际取消、输出清理和同Player重新导出通过。全片37,951帧全部解码，帧数/帧序/CFR PTS、音频解码与包连续性、音画流起止通过；未做全片像素参考对照或完整试听。Python91、Node269与Unity构建/既有42项离屏、队列和动画检查通过，见[验证记录](validation.md)。

旧不限帧矩阵有持续3D提交确认长等待；用户提出可能同时运行游戏，缺少对应负载记录，仍为待测线索。全片最大提交确认32.38ms，未重现不等于修复。原生日志为CPU墙钟，1Hz整卡利用率也不能替代GPU时间戳或逐进程分析。

全片队列高水位8帧/62,148状态字节，汇总报告51,874字节；内存仅采样Player和Electron主进程，不包含renderer，不能证明全应用无泄漏。实际视频素材、设备故障、所有取消时机和编码前颜色边界仍待验证。

下一步先完成用户观感验收与普通导出接入，再按计时拆分收尾成本；是否增加多画面缓冲取决于新证据。保留游戏目录只读、当前受管理资源、用户作品保护与[单build回退规则](local-builds.md)。此提交不发布或安装GPU用户版本。
