# 工程验证与故障排查

本页是 GSS 的实现经验。准备生成工程、调整动作层或处理播放异常时查阅；先以当前源码和文档核对能力，不据此自动扩大成软件维护任务。

## 资源与工程结构

- 仅使用当前游戏对应的有效受管理解包批次。批次失效应走当前资源准备流程，禁止恢复历史样本路径或跨批次拼接。游戏目录只读。
- 工程生成可参考当前 `apps/desktop/electron/project-store.js` 的格式校验、`apps/desktop/ui/story-timeline.js` 的排时、`apps/desktop/ui/animation-layers.js` 的动作／表情分层；文件路径相对于仓库。这些 API、模块名和 schema 需随版本复核。
- 区分角色对象、基础动画轨、常驻层、表情／口型轨、相机轨、出镜变换轨、场景轨、字幕轨和声音效果。不要靠显示名猜测动作类型，也不要假设 JSON 已包含外置媒体。
- 按当前实现，用稳定的剧情单元绑定相机、出镜与滤镜；配音改变后应随主线重排。单次动作保持自身长度时，可用仅起点绑定和 `keys: keep`；镜头覆盖整段时再选择起止绑定。先验证当前 `reflow` 语义。
- 本轮发现对整句使用 `keys: scale` 会连淡入淡出时间一起拉伸。若希望绝对秒数，明确采用保留时长的方案，并检查重排前后动作长度与淡化时间，而非只改一次数值。
- 按角色和台词意图在当前动作、表情目录中找素材。思考、追问、吃惊可分别用 `think`、`ask`、`odoroku` 作检索词。取样核对身体幅度及面部表现，角色可延续同一身体姿势，只在改口处换眉眼。
- 句中改口或领悟时，让动作、表情各自绑定触发它的对白。可用 `storyTiming = {start: {unitId, edge: "speechStart", offset: t}, keys: "keep"}`，其中 `t` 为该词或停顿相对本句语音开始的秒数。若动作有蓄势，把进入点稍微前移，让抬头、收手等看得见的变化落在重音上。重新 Cook 后核对实际语速和句内偏移。
- 同一手势跨句延续时，可把片段终点绑在下一次收势或转折处，眉眼表情在自己的落点调整。当前 `layerPlayback: true`、`loop: false` 可在进入动画结束后保持末态，`keys: keep` 可保留渐变秒数。缺独立退出素材时可用 `fadeOut` 混合回常驻。复查实际画面中身体是否顺畅衔接，以及眉眼表情与对白嘴形能否同时读出。

## 静态姿势＋原生律动

以下是当前 GSS 常驻层结构示意，实际 assetId 应从当前目录解析，不能原样使用占位值：

```json
{
  "id": "actor-idle-rhythm",
  "kind": "animation",
  "enabled": true,
  "weight": 100,
  "assetId": "从当前批次解析的律动素材ID",
  "blendMode": "additive",
  "scope": "full",
  "condition": "always",
  "loop": true
}
```

基础姿势由角色 `idleAssetId` 指向 `isPose: true` 的素材。示例 `condition: always` 让原生增量律动在基础动画进入、保持末态及返回常驻期间持续叠加；`resident` 仅在没有基础动作时生效，因此会让跨句基础片段的保持段失去律动。两者不是同义字段。`weight: 100` 只是试排起点，按幅度及骨盆／头部／手势取样调整。原生增量素材才使用 additive；普通动画不因命名或低权重就变成合法增量动画。

检查时在源进入动画结束之后、片段渐出之前选两个不同律动相位，核对基础采样时间已钳制而增量层时间仍在推进，并观察骨骼或实际画面差异；再跳出此段、跳回同一时间验证可重复性。不要把口型、字幕变化当作身体律动的证据。

## 角色下沉的诊断

先区分相机失准、外层变换、骨架内部位置、动画混合及可能的物理影响。记录同一角色同一动作时间的 root、Hips、Head 位置，再比较首次播放、动作返回、混合后重播和跳转回看。

2026-11-16 本地复现过一种明确原因：同一个 AnimationClipPlayable 仍连在旧 AnimationMixerPlayable 或身体分层器上，新连接被 Unity 拒绝。缺少有效身体输入时，Humanoid 骨盆位置异常，尽管外层 Transform.position 仍是零。当前修复在两方向切换前释放旧输入：`CreatorAnimationLayers.DetachBase()` 和 `CreatorPrototypePlayer.ClearBlend()`，主角色与其他角色都需覆盖。

这只是已证实的一类根因，不是所有下沉问题的通用结论。重现时检查日志中的 `Cannot connect output 0`、图连接和骨骼位置；不能先改 root Y、相机高度或原始动画掩盖故障。没有对应日志／数值证据时保留其他假设。

## 机位与效果验证

- 在动作前、中、后检查头顶、眼位、上半身、手势与字幕安全区。侧面 45° 既要检查相机朝向也要检查其绕角色的位置；只改欧拉角会让人物偏离画面。
- 腰部以上不能用固定距离保证：比较制作人图片与每个角色的实际屏幕占比，同时调整相机距离和高度。多人画面优先调整站位与横向留白，避免为容纳角色而把下沿降到大腿。
- 镜头的 FOV 与距离共同决定主体大小。试大头特写时移动相机并检查透视，避免只加 FOV。
- 若 `SetBackground`／`FitBackground` 将 2D 背景挂在相机下，相机平移只会改变角色关系。2D 空镜应使用有效批次背景对应的画面图层变换能力，先确认实际可动画属性。
- 回忆声音效果属于声音处理链。当前试用回声的尾音在片段末尾裁断，不自动延长剧情；边界与听感需试听。叠加心理暗角时确认字幕层序与透明度正确。

## 缓存占用标记的用途与边界

标记表示“有会话可能仍在使用这个缓存”，主要防止另一个实例重新解包、切换或清除正在被 Player／宿主使用的批次。正常关闭应在使用进程退出后释放；异常退出可能留下标记。它不是“每次退出都应该永久保留”的记录。

PID 已消失也不能立即推断缓存空闲：可能仍有宿主、导入器或 Player 子进程，或 PID 被系统重新分配。出现标记异常时，先核对标记身份、实际进程、当前批次与延后清理记录，不把删除锁文件等同于修复缓存。不得顺便重解包、删批次或清除用户作品。
